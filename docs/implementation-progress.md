# Implementation progress

## Batch 1 — invoice correctness and issuance, 2026-10-03

Implemented from the project review:

- Shared exact-decimal multiplication, half-up rounding per line, and totals summed in integer cents. UI, history and both language renderers use the same calculation module. Amounts in words carry cents into euros.
- Issuance validation for seller/buyer names, actual calendar dates and due-date order, 1–200 meaningful rows, positive quantities with up to three decimals and prices with up to two decimals. Other party/tax/bank fields remain optional. The UI reports field errors before submission.
- Local calendar date defaults and due-date recalculation until the user edits the due date. Numeric inputs preserve partially typed decimals.
- Atomic server-side number reservations, padding preservation, persistent used-number records and a sequence independent of deleted invoices. Custom older numbers cannot rewind the current series. Existing duplicate numbers are preserved if present; all future reuse is rejected.
- Persistent idempotency records: retrying one generation returns its stored ZIP without rendering/sending again. A different payload with the same key is rejected. A retry after deletion returns Gone. Failed rendering releases its reservation; interrupted reservations expire after five minutes. The browser retains a key for the unchanged form while that form remains open.
- Read-only issued form, Download saved invoice and an explicit New invoice action. Automatic numbering is assigned at generation; manual edits select custom numbering.
- Versioned SQLite migration. Original rows keep calculation version 0; new rows use version 1 and retain total cents. Original invoice payloads, totals and ZIPs are preserved. Regeneration retains the saved calculation version, using the current renderer/word formatting.
- Server-side deletion conflicts during regeneration/email operations, with locks released on completion/failure. This guard assumes the current single-backend deployment.
- Docker Node 24 for both services, lockfile-based npm ci, the same Vite/plugin versions as development, shared build inputs and loopback-only publication.
- Repaired end-to-end authentication checks, non-mutating backend lint, invoice retry/concurrency/rounding regression tests and a committed browser smoke check with mocked APIs.

## Yearly taxes and theoretical take-home — 2026-10-04

Implemented `docs/yearly-tax-summary-plan.md` with an account-owned Yearly taxes view. The first release supports the 2026, accrual, 30% expense/no-extra-pension profile. Users review their profile and obligated PSD months once per year; other years retain income visibility without applying unsupported tax rules. VAT features are excluded as requested.

- Annual GPM credit/progressive bands and capped VSD/PSD use exact BigInt rational arithmetic with cent-rounded estimates. Partial-month PSD and broader GPM situations remain incomplete rather than assumed zero. These are budgeting estimates, not whole-euro declaration calculations.
- Full invoice revenue remains in theoretical take-home. The 30% allowance reduces the tax base without being deducted as cash spending or added twice. Annual taxes are allocated to monthly income with deterministic cent remainders; PSD minimums remain on their obligated months. The calendar-year average divides annual take-home by twelve.
- Migration v3 adds per-account/year settings, earned-date metadata and a constrained account-owned entries table for signed income adjustments and positive tax payments. Unique request keys prevent duplicate entries after a lost response. Payments are assigned to the covered tax year independently of their payment dates.
- Annual income queries all invoices rather than the paginated history response. New invoice totals use saved cents; legacy totals preserve their originally displayed amounts. Regeneration does not duplicate income. Earned-date edits, bulk date review, signed adjustments, payment editing/deletion and CSV export are available.
- Summary and CSV share a consistent database snapshot. Authentication and account ownership apply to reads and mutations. CSV escapes text and neutralizes spreadsheet formulas; the page refreshes on opening, focus and changes, and account changes remount its state.
- History deletion continues to remove invoices; the confirmation now explains the effect on yearly income. No original invoice payloads or ZIPs are rewritten by tax features.

### First-start permissions correction

The Debian guide's root ownership/permissions command now also grants FOWNER alongside CHOWN and DAC_OVERRIDE. After changing ownership to UID 1000, chmod requires FOWNER in a container with all capabilities dropped; DAC_OVERRIDE alone does not grant it. The exact ownership/chmod sequence was verified in a network-disabled disposable Linux container, including already UID-1000-owned backup directories: directories are 0700, DB is 0600 and all are owned by UID 1000.
